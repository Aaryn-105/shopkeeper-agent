## 1. 文档概述

### 1.1 编写目的

本文档旨在全面、系统地描述「电商问数（Shopkeeper Agent）」项目的功能需求与非功能需求，为后续的系统设计、开发、测试和验收提供明确依据。本文档面向电商数据分析场景，定义了一套基于大语言模型的自然语言转 SQL（NL2SQL）智能问数系统的完整需求边界，确保项目干系人对系统目标、功能范围、质量标准达成一致认知。

本文档将作为以下工作的基准文件：
- 系统架构设计与技术选型的输入依据

- 测试团队制定测试计划与测试用例的基准
- 项目验收与质量评估的标准参照
- 产品迭代与需求变更的基线文档

### 1.2 项目范围

**包含范围：**
- 元数据知识库构建与管理（表、字段、指标、字段取值的结构化管理与索引构建）
- 问数智能体核心工作流（关键词抽取、多路召回、合并过滤、SQL生成、校验、纠错、执行）
- 后端 API 服务（问数接口、元数据管理接口、系统管理接口）
- 前端交互界面（问数对话页、执行过程可视化、结果展示）
- 系统基础配置与运维监控能力

**不包含范围（本期不实现）：**
- 多租户隔离与用户权限分级管理
- 复杂 SQL 安全审计与合规审查
- 查询结果缓存与性能治理体系
- 完整的模型评测与效果评估平台
- 多轮对话记忆与上下文追问

## 2. 业务背景与目标

### 2.1 业务痛点

在电商企业日常运营中，数据分析需求呈现出频次高、场景杂、门槛高的特点，当前面临的核心痛点包括：

**痛点一：数据分析门槛高，供需矛盾突出**
- 业务运营、产品、市场等非技术岗位人员普遍不会编写 SQL，无法直接从数据仓库获取分析结果
- 数据分析师资源有限，大量简单、重复的查数需求占用了分析师的核心精力
- 需求排队周期长，业务方从提出问题到拿到结果往往需要数小时甚至数天，错失决策时机

**痛点二：数据理解成本高，口径难以统一**
- 企业数据仓库表多、字段多，即使是技术人员也难以记住所有表结构和字段含义
- 指标定义分散，同一指标在不同部门可能有不同口径，导致数据认知不一致
- 新人上手数据的周期长，需要反复向数据团队确认表和字段的用途

**痛点三：传统 BI 工具灵活性不足**
- 固定报表只能覆盖预先设计好的分析场景，无法应对突发的、探索性的问题
- 自助 BI 工具仍需要用户理解维度、度量等概念，学习成本较高
- 当问题涉及多表关联、复杂过滤时，传统工具的易用性急剧下降

**痛点四：大模型裸写 SQL 可靠性不足**
- 直接将问题交给大模型生成 SQL，模型缺乏对企业数据结构的了解，错误率高
- 表和字段太多时，上下文长度有限，无法一次性将所有元数据传入
- 生成的 SQL 缺乏校验机制，可能存在语法错误、逻辑错误甚至安全风险

### 2.2 项目目标

**总体目标：** 构建一套面向电商数据分析场景的 NL2SQL 智能问数系统，使用户能够通过自然语言提问，快速、准确地从数据仓库中获取分析结果，降低数据分析门槛，提升决策效率。

**具体目标：**

| 目标类别 | 目标描述 | 量化指标 |
|---------|---------|---------|
| 功能目标 | 实现完整的元数据知识库管理能力 | 支持至少 5 张数仓表、20+ 字段、5+ 业务指标的结构化管理与检索 |
| 功能目标 | 实现基于 LangGraph 的多阶段问数智能体 | 包含至少 12 个处理节点，覆盖关键词抽取→召回→过滤→生成→校验→执行全链路 |
| 效果目标 | 常见电商分析问题 SQL 生成准确率 | 标准测试集准确率 ≥ 85% |
| 性能目标 | 单条问数请求端到端响应时间 | P95 ≤ 30 秒（含 SQL 执行时间） |
| 体验目标 | 前端执行过程可视化 | 支持 10+ 个节点的实时进度展示 |
| 工程目标 | 完整的前后端交付 | 提供可独立部署的后端服务与前端页面 |

### 2.3 业务价值

**降本增效：**
- 将简单、重复的查数需求自动化释放数据分析师人力，使其聚焦于更有价值的深度分析
- 业务人员自助获取数据，减少跨部门沟通成本和等待时间，预计单次查数耗时从小时级降至秒级

**数据民主化：**
- 降低数据分析的技术门槛，让更多业务角色能够直接用数据支撑决策
- 统一指标口径，减少因口径不一致导致的沟通误解和决策偏差

**技术沉淀：**
- 探索大模型在企业数据分析场景的工程化落地路径
- 构建可复用的元数据知识库与智能问数框架，为后续扩展到更多业务域奠定基础

### 2.4 预期收益

| 收益类型 | 具体收益 | 衡量方式 |
|---------|---------|---------|
| 效率收益 | 业务人员自助查数，减少数据分析师重复性工作 | 常规分析需求自助满足率 ≥ 70% |
| 时间收益 | 查数响应时间从天/小时级缩短至秒级 | 单次查询平均耗时 ≤ 30 秒 |
| 质量收益 | 统一指标口径，减少数据理解偏差 | 指标口径一致率达到 100% |
| 能力收益 | 形成可复用的 NL2SQL 技术框架 | 支持快速扩展到新的业务域和数据表 |

## 3. 用户角色与使用场景

### 3.1 用户角色分析

#### 3.1.1 业务运营人员

- **角色描述：** 电商运营、活动运营、品类运营等一线业务人员
- **技术水平：** 不会 SQL，对数据仓库结构基本不了解
- **核心诉求：** 快速获取运营数据，支撑日常决策；用最自然的语言提问，无需学习专业工具
- **典型问题：**
  - "华北地区上个月的销售总额是多少？"
  - "各品牌销量排名前10的商品有哪些？"
  - "黄金会员的订单金额占比是多少？"

#### 3.1.2 产品经理

- **角色描述：** 负责电商产品功能设计与迭代的产品人员
- **技术水平：** 具备基础数据分析能力，可能了解简单 SQL，但不熟练
- **核心诉求：** 快速验证产品假设，获取用户行为相关数据；支持探索性数据分析
- **典型问题：**
  - "男性用户和女性用户的客单价分别是多少？"
  - "2025年第一季度各月的 GMV 趋势如何？"

#### 3.1.3 数据分析师

- **角色描述：** 专业数据分析人员，负责深度分析与报表建设
- **技术水平：** 熟练掌握 SQL，熟悉数仓结构
- **核心诉求：** 减少简单重复查询的工作量，将精力聚焦于深度分析；快速获取初步结果后再深入挖掘
- **典型问题：**
  - "按大区和品类交叉统计销售额，输出透视表形式"
  - "各会员等级的订单量和订单金额分布"

#### 3.1.4 系统管理员

- **角色描述：** 负责系统配置、元数据维护、运维监控的技术人员
- **技术水平：** 具备数据库和系统运维能力
- **核心诉求：** 便捷的元数据管理工具；系统运行状态可观测；问题可定位
- **典型操作：**
  - 新增/修改表元数据配置
  - 执行元数据同步脚本
  - 查看系统运行日志和错误信息

### 3.2 典型使用场景

#### 场景一：日常经营数据查询

**场景描述：** 运营人员在每日晨会前，需要快速了解前一天的核心经营数据。

**操作流程：**
1. 运营人员打开电商问数系统
2. 在输入框中输入："昨天各大区的销售额是多少？"
3. 系统实时展示执行过程：抽取关键词→召回字段→召回指标→召回取值→合并→过滤→生成 SQL→校验→执行
4. 系统返回各大区销售额的表格结果
5. 运营人员查看结果，准备晨会材料

**预期结果：** 10 秒内获得查询结果，SQL 生成准确，数据与数仓中一致。

---

#### 场景二：活动效果复盘分析

**场景描述：** 活动结束后，运营人员需要从多个维度分析活动效果。

**操作流程：**
1. 运营人员输入："活动期间华东地区各品类的销售总额排名"
2. 系统识别"活动期间"需要时间范围（假设系统已知最近活动时间或用户补充说明）
3. 智能体自动关联地区维度、商品品类维度和订单金额指标
4. 生成多表关联 SQL 并执行
5. 返回按品类排序的销售总额列表

**预期结果：** 正确关联事实表与多张维度表，分组聚合逻辑准确，排序正确。

---

#### 场景三：用户画像探索

**场景描述：** 产品经理想了解不同用户群体的消费特征差异。

**操作流程：**
1. 产品经理输入："各会员等级的平均订单金额和订单数量"
2. 系统识别需要统计 AOV（平均订单金额）和订单量两个指标
3. 按会员等级维度分组统计
4. 返回包含会员等级、平均订单金额、订单数量三列的结果表

**预期结果：** 正确识别多个指标和分组维度，聚合计算准确。

---

#### 场景四：元数据维护与同步

**场景描述：** 数据团队新增了数仓表，需要将新表纳入问数系统。

**操作流程：**
1. 系统管理员更新元数据配置文件，添加新表的表信息、字段信息和指标定义
2. 执行元数据同步脚本
3. 系统自动完成：读取数仓表结构→写入 MySQL 元数据库→构建 Qdrant 向量索引→构建 Elasticsearch 全文索引
4. 管理员验证新表的字段和指标能否被正确召回

**预期结果：** 同步过程可重复执行，支持增量更新；同步完成后新表可被问数智能体正确检索和使用。

## 4. 功能需求

### 4.1 元数据知识库管理模块

元数据知识库是整个问数系统的语义基础，负责将数据仓库中的表、字段、指标和字段取值整理成可检索的知识体系。本模块包含元数据配置、元数据库管理、向量索引管理、全文索引管理和同步脚本五大功能。

#### 4.1.1 元数据配置管理

**功能描述：** 提供配置驱动的元数据定义能力，支持以 YAML 配置文件的方式定义需要纳入元数据知识库的表、字段和指标。

**输入：**
- YAML 格式的配置文件，包含表列表、字段列表、指标列表及其业务语义

**输出：**
- 结构化的配置对象，可被同步脚本读取和处理

**业务规则：**
1. 配置文件支持定义表的基本信息，包括表名、表角色（事实表/维度表）、表描述
2. 配置文件支持定义字段的完整信息，包括字段名、字段角色（主键/外键/维度/度量）、字段描述、字段别名、示例值
3. 配置文件支持定义业务指标，包括指标名、指标描述、相关字段、指标别名
4. 配置文件支持增量更新，可单独新增或修改某张表的配置
5. 配置文件需有明确的格式规范和校验机制，避免格式错误导致同步失败

**优先级：** P0

---

#### 4.1.2 元数据库管理

**功能描述：** 在 MySQL 中构建结构化元数据库，保存表信息、字段信息、指标信息以及字段与指标的关联关系，作为元数据知识库的权威数据源。

**输入：**
- 配置文件中的表、字段、指标定义
- 数据仓库中查询到的真实表结构和字段类型

**输出：**
- MySQL 元数据库中的 4 张核心表：`table_info`、`column_info`、`metric_info`、`column_metric`

**业务规则：**
1. **table_info 表**：存储表的基本信息，至少包含表名、表角色（fact/dimension）、表描述、创建时间、更新时间
2. **column_info 表**：存储字段的完整信息，字段结构如下：
   - id：字段唯一标识，格式为 `表名.字段名`
   - name：字段名称
   - type：字段数据类型（如 varchar(64)、decimal(10,2)、int 等）
   - role：字段角色（primary_key/foreign_key/dimension/measure）
   - examples：字段示例值列表
   - description：字段业务描述
   - alias：字段别名列表
   - table_id：所属表的标识
3. **metric_info 表**：存储业务指标定义，至少包含指标 ID、指标名称、指标描述、相关字段列表、指标别名列表
4. **column_metric 表**：存储字段与指标的多对多关联关系，包含字段 ID 和指标 ID
5. 元数据库中的数据以配置文件为权威来源，同步时采用覆盖更新策略
6. 字段的 type 和部分 examples 从数据仓库真实查询获取，确保与实际数仓结构一致

**优先级：** P0

---

#### 4.1.3 向量索引管理

**功能描述：** 将字段信息和指标信息转换为向量表示，存储到 Qdrant 向量数据库中，支持基于语义相似度的召回。

**输入：**
- 元数据库中的字段信息（字段名、描述、别名等）
- 元数据库中的指标信息（指标名、描述、别名等）
- Embedding 服务提供的文本向量化能力

**输出：**
- Qdrant 中的字段向量集合和指标向量集合（两个独立的 collection）

**业务规则：**
1. 字段向量索引使用字段名、字段描述、字段别名的组合文本进行向量化
2. 指标向量索引使用指标名、指标描述、指标别名的组合文本进行向量化
3. 向量模型采用 BAAI/bge-large-zh-v1.5，向量维度为 1024
4. 向量索引支持相似度检索，返回 Top-K 最相关结果
5. 向量索引的构建与更新由同步脚本统一驱动，确保与元数据库数据一致
6. 向量索引支持按表过滤，便于后续按业务域拆分检索

**优先级：** P0

---

#### 4.1.4 全文索引管理

**功能描述：** 将维度字段的真实取值存储到 Elasticsearch 中，支持基于关键词匹配的字段取值检索。

**输入：**
- 数据仓库中维度字段的真实取值
- 字段标识信息（用于标记取值所属的字段）

**输出：**
- Elasticsearch 中的字段取值索引

**业务规则：**
1. 全文索引仅覆盖"文本型、维度型、可能作为过滤条件"的字段，如地区、品牌、品类、会员等级、商品名称等
2. 度量字段（如 order_amount、order_quantity）和数值型时间字段不建立全文索引
3. 每条索引记录包含三个核心字段：id（取值唯一标识）、value（字段实际取值）、column_id（所属字段标识）
4. 全文检索使用 IK 中文分词器，支持中文关键词的精确匹配和模糊匹配
5. 检索结果需返回匹配的取值及其所属字段，便于后续将值挂回对应字段
6. 字段取值的数量较大时，支持抽样或 Top-N 策略，优先索引高频取值

**优先级：** P0

#### 4.1.5 元数据同步脚本

**功能描述：** 提供统一的元数据同步工具脚本，根据配置文件自动完成从数据仓库到元数据知识库的全量/增量同步。

**输入：**
- 元数据配置文件（YAML 格式）
- 数据仓库连接信息
- Qdrant、Elasticsearch、Embedding 服务连接信息

**输出：**
- 同步执行日志
- 更新后的元数据库、向量索引、全文索引

**业务规则：**
1. 同步脚本支持命令行调用，执行方式明确（如 `uv run python -m app.scripts.build_meta_knowledge`）
2. 同步流程按以下顺序执行：
   - 读取配置文件，解析表、字段、指标定义
   - 查询数据仓库，获取表结构、字段类型和示例值

   - 为字段信息构建向量索引（写入 Qdrant）
   - 为指标信息构建向量索引（写入 Qdrant）

3. 同步脚本支持幂等执行，重复执行不会导致数据重复或错误
4. 同步过程需有详细的日志输出，记录每张表、每个字段、每条指标的同步状态
5. 同步失败时需明确报错，指出失败原因和位置，便于排查
6. 支持增量同步模式（后续版本可扩展），本期先支持全量同步

**优先级：** P0

### 4.2 问数智能体模块

问数智能体是系统的核心功能模块，基于 LangGraph 构建多阶段工作流，将用户的自然语言问题逐步转化为可执行的 SQL 查询并返回结果。智能体包含 12 个核心节点，涵盖理解问题、召回知识、整理上下文、生成 SQL、校验执行五个阶段。

#### 4.2.1 关键词抽取节点（extract_keywords）

**功能描述：** 从用户的自然语言问题中提取核心关键词，用于后续的检索召回。采用 jieba 的 TF-IDF 关键词提取算法，过滤停用词和无意义表达，保留对查询有实际帮助的核心词。

**输入：**
- 用户原始问题（query: str）

**输出：**
- 关键词列表（keywords: List[str]）
- 保留原始问题作为语义兜底

**业务规则：**
1. 使用 jieba 的 TF-IDF 关键词提取算法进行关键词抽取
2. 提取的关键词数量根据问题长度自适应，通常为 3-10 个
3. 过滤"的、了、一下、帮我、请问"等停用词和无意义口语表达
4. 保留用户原始问题，作为后续向量检索的补充输入，避免关键词抽取遗漏语义
5. 关键词抽取结果需支持中文分词的准确性，专业术语和品牌名不被错误切分
6. 节点执行完成后，通过 stream_writer 输出"抽取关键词"进度事件

**优先级：** P0

---

#### 4.2.2 字段信息召回节点（recall_column）

**功能描述：** 基于用户问题和关键词，从向量索引中检索最相关的字段信息，完成字段的粗召回。

**输入：**
- 用户原始问题（query: str）
- 关键词列表（keywords: List[str]）
- Qdrant 字段向量索引
- Embedding 服务

**输出：**
- 召回的字段信息列表（retrieved_column_infos: List[ColumnInfo]）

**业务规则：**
1. 先基于关键词和问题文本进行关键词扩展，生成更适合字段检索的扩展关键词列表
2. 关键词扩展通过大模型完成，提示词模板为 `extend_keywords_for_column_recall.prompt`
3. 使用扩展后的关键词和原始问题分别进行向量检索，取并集或加权合并
4. 向量检索返回 Top-K 个最相关的字段（K 值可配置，默认 20）
5. 召回结果包含字段的完整信息：字段名、类型、角色、描述、别名、示例值、所属表
6. 召回阶段遵循"宁可多召回，不可漏召回"的原则，为后续精筛留出空间
7. 节点执行完成后，通过 stream_writer 输出"召回字段信息"进度事件

**优先级：** P0

---

#### 4.2.3 指标信息召回节点（recall_metric）

**功能描述：** 基于用户问题和关键词，从向量索引中检索最相关的业务指标信息，完成指标的粗召回。

**输入：**
- 用户原始问题（query: str）
- 关键词列表（keywords: List[str]）
- Qdrant 指标向量索引
- Embedding 服务

**输出：**
- 召回的指标信息列表（retrieved_metrics: List[MetricInfo]）

**业务规则：**
1. 先基于关键词和问题文本进行关键词扩展，生成更适合指标检索的扩展关键词列表
2. 关键词扩展通过大模型完成，提示词模板为 `extend_keywords_for_metric_recall.prompt`
3. 使用扩展后的关键词和原始问题分别进行向量检索，取并集或加权合并
4. 向量检索返回 Top-K 个最相关的指标（K 值可配置，默认 10）
5. 召回结果包含指标的完整信息：指标名、描述、相关字段、别名
6. 支持识别用户问题中的口语化指标表达（如"销售总额"对应 GMV，"平均单价"对应 AOV）
7. 节点执行完成后，通过 stream_writer 输出"召回指标信息"进度事件

**优先级：** P0

---

#### 4.2.4 字段取值召回节点（recall_value）

**功能描述：** 基于用户问题和关键词，从 Elasticsearch 全文索引中检索匹配的字段取值，完成字段值的粗召回。

**输入：**
- 用户原始问题（query: str）
- 关键词列表（keywords: List[str]）
- Elasticsearch 字段取值全文索引

**输出：**
- 召回的字段取值列表（retrieved_values: List[ValueInfo]），每个值包含 value 和 column_id

**业务规则：**
1. 使用关键词进行全文检索，匹配字段取值
2. 全文检索使用 IK 分词器，支持中文分词匹配
3. 检索结果包含匹配的取值文本和该取值所属的字段标识（column_id）
4. 返回 Top-K 个最匹配的字段取值（K 值可配置，默认 30）
5. 支持模糊匹配和近义词匹配，如"华北"能匹配"华北地区"相关取值
6. 同一字段的多个匹配值需聚合返回，便于后续统一挂回字段
7. 节点执行完成后，通过 stream_writer 输出"召回字段取值"进度事件

**优先级：** P0

---

#### 4.2.5 召回信息合并节点（merge_retrieved_info）

**功能描述：** 将三路召回（字段、指标、字段取值）的分散结果整理为结构化的上下文信息，按表归组、按字段挂值，形成适合大模型理解的层次化结构。

**输入：**
- 字段召回结果列表（retrieved_column_infos）
- 指标召回结果列表（retrieved_metrics）
- 字段取值召回结果列表（retrieved_values）
- MySQL 元数据库（用于补全主外键等关联信息）

**输出：**
- 表信息上下文（table_infos）：按表分组的层次化表结构信息
- 指标信息上下文（metric_infos）：整理后的指标定义及其相关字段

**业务规则：**
1. 根据字段的 table_id 属性，将召回的字段按所属表重新归组
2. 每张表的信息包括：表名、表角色、表描述、字段列表
3. 每个字段的信息包括：字段名、类型、角色、描述、别名、示例值
4. 将召回的字段取值根据 column_id 挂回到对应字段的示例值或候选取值中
5. 根据召回的指标，通过 column_metric 关联找到指标相关的字段，补充到表信息中
6. 自动补全生成 SQL 必需的主外键字段（如 customer_id、product_id、region_id、date_id），即使它们没有被直接召回
7. 表信息以 YAML 风格的层次化结构组织，便于大模型阅读和理解
8. 指标信息同样整理为结构化列表，包含指标名、描述、相关字段、别名
9. 节点执行完成后，通过 stream_writer 输出"合并召回信息"进度事件

**优先级：** P0

---

#### 4.2.6 表信息过滤节点（filter_table）

**功能描述：** 借助大模型，结合用户原始问题，对合并后的表信息进行精筛，剔除无关表和无关字段，保留生成 SQL 真正需要的表结构上下文。

**输入：**
- 用户原始问题（query: str）
- 合并后的表信息上下文（table_infos）
- 大模型服务

**输出：**
- 过滤后的表信息上下文（filtered_table_infos）

**业务规则：**
1. 使用大模型对召回的表和字段进行语义判断，筛选与当前问题最相关的部分
2. 过滤使用专用提示词模板 `filter_table_info.prompt`
3. 过滤标准：与问题中的分析维度、度量指标直接相关的表和字段保留，明显无关的剔除
4. 必须保留主外键关联字段，即使它们不是问题直接关注的对象
5. 过滤后仍需保持层次化结构（表→字段），格式与过滤前一致
6. 过滤结果需保证生成 SQL 所需的最小信息完整，不能因过度过滤导致 SQL 生成失败
7. 节点执行完成后，通过 stream_writer 输出"过滤表信息"进度事件

**优先级：** P0

---

#### 4.2.7 指标信息过滤节点（filter_metric）

**功能描述：** 借助大模型，结合用户原始问题，对召回的指标信息进行精筛，只保留与当前问题最相关的业务指标。

**输入：**
- 用户原始问题（query: str）
- 合并后的指标信息上下文（metric_infos）
- 大模型服务

**输出：**
- 过滤后的指标信息上下文（filtered_metric_infos）

**业务规则：**
1. 使用大模型对召回的指标进行语义判断，筛选与当前问题最相关的指标
2. 过滤使用专用提示词模板 `filter_metric_info.prompt`
3. 过滤标准：指标名称、描述或别名与问题语义匹配的保留，明显无关的剔除
4. 保留指标的完整信息：指标名、描述、相关字段、别名
5. 支持一个问题命中多个指标的场景（如问题同时问到销售额和订单量）
6. 节点执行完成后，通过 stream_writer 输出"过滤指标信息"进度事件

**优先级：** P0

---

#### 4.2.8 额外上下文补充节点（add_extra_context）

**功能描述：** 在生成 SQL 之前，补充不直接属于表结构但会影响 SQL 正确性的环境信息，包括当前时间、数据库类型和版本等。

**输入：**
- 当前系统时间
- 数据库类型（MySQL）
- 数据库版本号
- 过滤后的表信息和指标信息

**输出：**
- 补充完整的上下文信息，供后续 SQL 生成使用

**业务规则：**
1. 补充当前时间，格式为标准日期时间格式（如 YYYY-MM-DD HH:mm:ss）
2. 补充数据库类型（MySQL），使大模型生成符合 MySQL 方言的 SQL
3. 补充数据库版本号，便于大模型考虑版本特性差异
4. 时间信息用于处理涉及"今天"、"昨天"、"上个月"、"去年"等相对时间表达的问题
5. 数据库类型和版本信息用于确保 SQL 语法、函数使用与执行环境兼容
6. 补充信息作为上下文的一部分，与表信息、指标信息一起传递给 SQL 生成节点
7. 节点执行完成后，通过 stream_writer 输出"补充额外上下文"进度事件

**优先级：** P1

---

#### 4.2.9 SQL 生成节点（generate_sql）

**功能描述：** 在完整上下文齐备的条件下，调用大模型生成符合业务需求的 SQL 查询语句。

**输入：**
- 用户原始问题（query: str）
- 过滤后的表信息上下文（filtered_table_infos）
- 过滤后的指标信息上下文（filtered_metric_infos）
- 额外上下文（当前时间、数据库类型及版本）
- 大模型服务

**输出：**
- 生成的 SQL 语句（sql: str）

**业务规则：**
1. 使用专用提示词模板 `generate_sql.prompt` 引导大模型生成 SQL
2. 生成的 SQL 必须使用上下文中提供的表名和字段名，不得编造不存在的表或字段
3. SQL 必须符合 MySQL 语法规范
4. 正确处理事实表与维度表的关联，JOIN 条件使用主外键
5. 正确识别聚合方式（SUM、COUNT、AVG 等）与业务指标的对应关系
6. 正确处理过滤条件（WHERE 子句），字段取值需与数仓中的真实值匹配
7. 正确处理分组统计（GROUP BY）与排序（ORDER BY）
8. 支持多维度组合查询、多指标同时统计
9. 生成的 SQL 需有良好的可读性，适当使用别名（AS）
10. 节点执行完成后，通过 stream_writer 输出"生成 SQL"进度事件及生成的 SQL 内容

**优先级：** P0

---

#### 4.2.10 SQL 校验节点（validate_sql）

**功能描述：** 在执行 SQL 之前，通过数据库的 EXPLAIN 机制对 SQL 进行语法和可行性预检查，尽早发现错误。

**输入：**
- 待校验的 SQL 语句（sql: str）
- 数据仓库连接

**输出：**
- 校验结果（校验通过/校验失败）
- 错误信息（error: str，校验失败时填充）

**业务规则：**
1. 使用 MySQL 的 EXPLAIN 语句对 SQL 进行预检查
2. EXPLAIN 不会真正执行查询，只是分析执行计划，不会对数据仓库造成负载压力
3. 校验通过的标准：EXPLAIN 正常返回执行计划，无语法错误
4. 校验失败时，捕获数据库返回的完整错误信息，包括错误码和错误描述
5. 校验通过时，将 error 字段设为 None，表示无错误
6. 校验失败时，将错误信息写入 state 的 error 字段，供后续校正节点使用
7. 节点执行完成后，通过 stream_writer 输出"校验 SQL"进度事件及校验结果

**优先级：** P0

---

#### 4.2.11 SQL 校正节点（correct_sql）

**功能描述：** 当 SQL 校验失败时，基于数据库返回的错误信息和原始上下文，调用大模型对 SQL 进行修正。

**输入：**
- 用户原始问题（query: str）
- 原始 SQL 语句（sql: str）
- 校验错误信息（error: str）
- 表信息上下文、指标信息上下文
- 大模型服务

**输出：**
- 校正后的 SQL 语句（sql: str，覆盖原始 SQL）

**业务规则：**
1. 仅在校验失败（error 不为 None）时触发本节点，通过条件边控制流程走向
2. 使用专用提示词模板 `correct_sql.prompt` 引导大模型进行 SQL 纠错
3. 提示词中需包含：原始问题、表结构上下文、原始 SQL、错误信息
4. 大模型需根据错误信息定位问题并修正 SQL，常见错误类型包括：
   - 表名或字段名拼写错误
   - 缺少必要的 JOIN 条件
   - 聚合函数使用不当
   - GROUP BY 字段缺失
   - 数据类型不匹配
   - SQL 方言语法错误
5. 校正后的 SQL 直接覆盖 state 中的 sql 字段
6. 本期校正仅执行一次，不做循环多轮校正
7. 节点执行完成后，通过 stream_writer 输出"校正 SQL"进度事件及校正后的 SQL

**优先级：** P1

---

#### 4.2.12 SQL 执行节点（run_sql）

**功能描述：** 将通过校验（或校正后）的 SQL 发送到数据仓库执行，获取查询结果并返回。

**输入：**
- 最终 SQL 语句（sql: str）
- 数据仓库连接

**输出：**
- 查询结果（result: List[Dict] 或 DataFrame 格式）
- 查询结果的列名列表

**业务规则：**
1. 到数据仓库（dw 库）执行 SQL 查询
2. 使用异步数据库驱动执行查询，避免阻塞服务
3. 查询结果以结构化格式返回，包含列名和数据行
4. 对查询结果的行数进行限制（如默认最多返回 1000 行），防止大数据量输出影响性能
5. 查询失败时，捕获异常并返回明确的错误信息
6. 记录 SQL 执行耗时，用于性能监控和优化分析
7. 节点执行完成后，通过 stream_writer 输出"执行 SQL"进度事件及最终查询结果
8. 执行成功后，工作流进入 END 节点，整个问数流程结束

**优先级：** P0

### 4.3 API 服务模块

API 服务模块是后端能力的对外出口，基于 FastAPI 构建，提供问数查询、元数据管理、系统管理等 RESTful 接口，并通过 SSE 实现问数过程的实时推送。

#### 4.3.1 问数查询接口

**功能描述：** 提供自然语言问数的核心 API，接收用户问题，驱动问数智能体执行，并通过 SSE 实时返回执行过程和最终结果。

**输入：**
- 用户问题（query: str）
- 可选参数：会话 ID、问题上下文等

**输出：**
- SSE 流式响应，包含多个事件类型：
  - progress 事件：节点执行进度
  - sql 事件：生成的 SQL 语句
  - result 事件：最终查询结果
  - error 事件：错误信息

**业务规则：**
1. 接口路径：`POST /api/ask` 或 `GET /api/ask/stream`
2. 支持 SSE（Server-Sent Events）流式响应，前端可实时接收进度
3. 每次请求创建独立的智能体执行实例，互不干扰
4. 请求参数需做合法性校验，问题长度限制在合理范围内（如最多 500 字符）
5. 空问题或明显非查询类问题需返回友好提示
6. 接口响应头需正确设置 Content-Type 为 `text/event-stream`
7. 支持 CORS，允许前端跨域调用
8. 每个请求生成唯一请求 ID，用于日志追踪和问题排查

**优先级：** P0

#### 4.3.2 元数据管理接口

**输入：**

- 过滤条件（表名、字段名等）
- 分页参数

**输出：**
- 元数据列表或详情
- 分页信息

**业务规则：**
1. 表信息查询接口：`GET /api/metadata/tables`，返回所有纳入知识库的表列表
2. 字段信息查询接口：`GET /api/metadata/columns`，支持按表名过滤
3. 指标信息查询接口：`GET /api/metadata/metrics`，返回所有业务指标列表
4. 支持分页查询，参数包括 page 和 page_size
5. 详情接口返回字段或指标的完整信息
6. 本期先提供查询接口，增删改接口可后续扩展（当前通过配置文件+同步脚本管理）
